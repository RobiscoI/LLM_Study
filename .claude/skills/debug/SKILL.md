# 장애 분석

`incident-analyst` 에이전트를 띄운다. **고쳐주는 것이 목적이 아니다** —
어디가 깨졌는지 스스로 찾는 절차를 만든다 (로드맵 4수준 = 분석).

## 먼저 줄 것

증상만 던져도 되지만, 있으면 훨씬 빨라진다:

- 에러 메시지 **원문** (요약하지 말 것)
- 재현 조건 — 항상인가 가끔인가, 언제부터인가
- 마지막으로 바꾼 것

## 진행

### 1. 사실 / 가설 분리

```
[사실]  관측된 것만. 에러 원문, 상태 코드, 로그 줄, 재현 조건
[가설]  추정. 각각에 "어떻게 확인하나"를 붙인다
```

"CORS 같다"는 **가설**이다. 사실 칸에 올리지 않는다.

### 2. 계층별 진단표

| 계층 | 확인할 것 | 명령어·도구 | 기대 결과 | 실제 |
|---|---|---|---|---|
| 브라우저 | 콘솔·Network 탭 | DevTools | | |
| 네트워크 | 요청이 닿았는가 | `curl -v` | | |
| 백엔드 | 라우팅·인증·예외 | 서버 로그 | | |
| DB / LLM | 쿼리·응답·타임아웃 | psql · API 로그 | | |

### 3. 이분 탐색

표를 다 채우지 않는다. **가운데를 먼저 친다** — "서버 로그에 요청이 찍혔는가?"
하나로 앞뒤 절반이 갈린다. 한 번에 한 계층씩, 결과를 받아서 범위를 좁힌다.

## 끝나면

**원인 → 가설 → 검증** 순서로 한 문단 정리. 주차 노트의 「오류 기록」 표에 붙인다
(매주 체크리스트 5번 = 오류 원인과 해결 과정 기록).

**재발 방지**도 한 줄 — 어떤 테스트나 로그가 있었으면 바로 잡혔을지.
