# evals — 평가 데이터와 스크립트

**21주차부터 채운다.** 지금은 형식만 정해 둔다 — 형식이 없으면 그때 데이터를 모으는
것부터 다시 시작하게 된다.

## 무엇을 만드나

로드맵 21주차: `30개 eval set · 회귀 테스트 · trace`, 완료 기준은 **변경 전후 결과표**.
최종 프로젝트 운영 기능에도 `30개 이상의 golden evaluation set` 과
`모델·prompt 버전별 정확성·근거성·속도·비용 측정` 이 들어 있다.

## golden set 형식

`evals/golden/<주제>.jsonl` — 한 줄에 한 케이스.

```jsonl
{"id": "rag-001", "question": "...", "expected": {"must_include": ["..."], "must_cite": ["doc-3"]}, "tags": ["rag", "인용"]}
{"id": "rag-002", "question": "...", "expected": {"must_refuse": true}, "tags": ["rag", "모름"]}
```

| 필드 | 뜻 |
|---|---|
| `id` | 고정. 결과표에서 케이스를 추적하는 키라 **바꾸지 않는다** |
| `question` | 입력 |
| `expected` | 정답 문자열이 아니라 **판정 조건**. LLM 출력은 매번 달라지므로 완전 일치를 기대하지 않는다 |
| `tags` | 집계 축 (주제·난이도·실패 유형) |

### `expected` 조건

| 키 | 통과 조건 |
|---|---|
| `must_include` | 나열된 표현이 모두 있다 |
| `must_not_include` | 하나도 없다 |
| `must_cite` | 지정 문서를 근거로 인용했다 |
| `must_refuse` | **모른다고 답했다** ← 16주차 완료 기준 "모르면 모름" |
| `max_latency_ms` / `max_cost_usd` | 성능 상한 |

## 케이스 구성 — 30개를 어떻게 채우나

성공 케이스만 모으면 평가가 아니라 데모가 된다.

| 비율 | 유형 |
|---|---|
| 40% | 정상 — 근거가 문서에 있고 답할 수 있다 |
| 20% | **답할 수 없음** — 문서에 없다. `must_refuse` |
| 20% | 경계 — 여러 문서에 흩어짐, 모순되는 근거, 아주 짧거나 긴 입력 |
| 10% | 함정 — 질문에 틀린 전제가 들어 있다 |
| 10% | **적대적** — prompt injection (22주차와 연결) |

## 결과표

`evals/results/<날짜>_<버전>.csv` 로 남긴다. 완료 기준이 **변경 전후 비교**이므로
한 번만 재면 의미가 없다.

```
case_id, 통과, 지연ms, 비용usd, 모델, prompt_ver, 비고
```

집계는 `tags` 별로. **전체 통과율 하나만 보면 어느 유형이 무너졌는지 안 보인다.**

## 주의

- **평가셋을 보고 프롬프트를 고치면 그 셋은 더 이상 평가가 아니다.** 일부를 손대지 않는
  hold-out 으로 남겨둔다.
- **LLM-as-judge 를 쓸 거면 판정자도 검증한다.** 사람 판정과 얼마나 일치하는지 표본으로 확인.
- 케이스는 **개발 중 실제로 겪은 실패**에서 나온 것이 가장 좋다. 주차 노트의
  「오류 기록」 표를 여기 옮긴다.
